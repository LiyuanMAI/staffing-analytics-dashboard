这个项目提供可运行代码和真实 SQL，但简历中的“独立开发”或“熟练掌握”应以你实际理解、修改和验证的部分为准。

## 五分钟演示顺序

1. 打开默认页，说明所有数据均为模拟数据，观察截至 2026-09-15。
2. 切换 Agency，再切换 Business unit，说明筛选条件相交，所有视图和导出共享同一范围。
3. 改变 Request date。解释为什么筛选一月的需求仍包含二月的录用结果，这是 cohort 口径。
4. 打开 Metric definitions，解释分母、空值、90 天观察窗口。
5. 打开 SQL 文件，解释先聚合再 JOIN 如何防止费用和人数重复。
6. 展示测试与运行结果，并说明尚未实现的生产后端和权限控制。

## 必须能回答的问题

- 为什么不能平均两个供应商的 Fill Rate？用 1/2 和 90/100 举例，整体为 91/102。
- 为什么请求、录用和费用需要分表？一次请求可对应多个岗位、多人和多条费用，单表重复需求数容易出错。
- 为什么零录用的 Cost per Hire 显示横杠？除数为零时成本仍存在，但单位录用成本没有定义。
- 为什么今年八月入职、五天后离职的人暂时不进入 90 天离职率？该定义对全部样本要求完整观察期，避免只把已知早离职者放进分子。
- TypeScript 的 union 和 interface 在哪里帮助避免错误？看 `Dimension`、`Filters` 和 `DashboardData`。
- 快速切换筛选时如何避免旧结果覆盖新结果？React effect 的清理函数让过期请求忽略结果。
- 为什么用参数化 SQL？值绑定避免将筛选输入当作 SQL；动态列名采用白名单。
- 为什么 PGlite 是 PostgreSQL 而不是 JavaScript 模拟查询？它通过 WebAssembly 执行 PostgreSQL 引擎；但浏览器单用户运行不是生产数据库服务。
- 如果改成真实多租户产品，如何保障权限？浏览器不能保存数据库凭据，应经已认证 API 获取租户身份并在服务端执行授权过滤或 PostgreSQL RLS。

## 建议你亲自完成的三个扩展

1. 增加“平均岗位等待天数”：明确只计算未填补岗位，写边界测试，解释与 Time to Hire 的差异。
2. 增加一个筛选维度，例如 Location，同步修改类型、生成器、SQL、界面、导出与测试。
3. 增加一个 API 服务和真实 PostgreSQL 连接，把现有查询移到服务端，并用两个虚构租户测试数据隔离。
